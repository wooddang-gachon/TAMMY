# TAMMY — 통합 기획 보고서 레포

이 레포는 **코드를 개발하는 곳이 아닙니다.** 팀원별로 각자 진행한 작업 디렉토리를 한곳에 모아두고,
그 위에서 **최종 기획 보고서(`PLANNING_REPORT.md`)를 공동으로 작성하기 위한** 레포입니다.

---

## 1. 레포 구성

| 경로 | 내용 |
| :--- | :--- |
| `PLANNING_REPORT.md` | **최종 산출물.** Ⅰ~Ⅸ 고정 목차 템플릿을 팀원들이 나눠 채웁니다 |
| `NASA_backEnd-main/` | 서비스 서버 (Node.js · TypeScript · Prisma) |
| `NASA_frontEnd-master/` | 클라이언트 (React 18 · TypeScript · Vite) |
| `tammy-ai-server-main/` | AI 서버 (Go · Gin · Genkit) |
| `docs/images/` | 보고서에 삽입하는 다이어그램 |
| `.claude/skills/report-align/` | 정렬 검토 스킬 (아래 3절) |

각 팀원 디렉토리는 원본 작업물의 스냅샷입니다. 보고서를 쓸 때 **주장의 근거는 문서가 아니라 이 소스코드에서 확인합니다.**

---

## 2. 협업 방식과 이 레포의 문제의식

작성 흐름은 이렇습니다.

```
팀원 각자 브랜치에서 PLANNING_REPORT.md의 담당 섹션 작성
        ↓
main 으로 PR
        ↓
같은 파일을 여럿이 건드리므로 충돌 발생 (의도된 것)
        ↓
충돌 해결 = "어떤 내용을 택하고 어떻게 결을 맞출지" 판단
        ↓
머지 후 전체 문서가 한 방향을 보는지 검토
```

**충돌은 사고가 아니라 판단 장치입니다.** 세 팀이 각자 자기 레포 관점에서 같은 서비스를 서술하기 때문에,
충돌 지점은 곧 "팀 간에 인식이 다른 지점"입니다. 이걸 기계적으로 봉합하면 보고서 안에서 서로 모순되는
문서가 됩니다. 그래서 머지할 때마다 **부분이 아니라 전체를 다시 읽고 방향을 맞추는 절차**를 둡니다.

---

## 3. 정렬 검토 스킬 (`report-align`)

머지 시점마다 충돌을 해결하고 전체 문서의 정렬 상태를 판정하는 로컬 스킬입니다.

**사용**: `/report-align` 또는 "정렬 검토해줘", "머지했어 확인해줘", "충돌 해결해줘"

**하는 일**

1. **충돌 해결** — conflict marker를 유형별로 판단해 해소합니다. 단, *같은 사실을 다르게 서술한* 충돌은 자동 해결하지 않고 소스 확인 후 사용자에게 확인받습니다.
2. **전체 정렬 검토** — 문서 전체를 5개 축(목차 구조 / 용어 / 사실 정합성 / 톤 / 중복·모순)으로 점검합니다.
3. **반영** — 판단 여지 없는 것만 직접 고칩니다. 내용 판단이 필요한 것은 선택지와 근거를 붙여 물어봅니다.
4. **보고** — 수정 내역, 확인 필요 항목, 미작성 섹션, 정렬 상태 한 줄 판정을 출력합니다.

판단의 정본은 **아래 4절의 정렬 원칙**입니다. 원칙에 답이 없으면 스킬은 임의로 정하지 않고 사용자에게 묻습니다.
반대로 팀에서 새로 합의한 규칙이 생기면 **4절에 추가해야** 다음 검토부터 적용됩니다.

---

## 4. 정렬 원칙 (정본)

> 이 절은 `report-align` 스킬이 정렬 여부를 판정하는 기준입니다. 팀 합의로만 수정합니다.

### 4.1 목차

- `PLANNING_REPORT.md`의 `##` (Ⅰ~Ⅸ), `###` 제목은 **템플릿 그대로 유지**합니다. 문구를 바꾸거나 번호를 재배치하지 않습니다.
- 섹션을 임의로 **추가하지 않습니다.** 넣고 싶은 내용은 기존 섹션 안의 `####` 이하로 넣습니다.
- 자기 담당이 아닌 섹션을 **삭제하지 않습니다.** 비워두거나 `*(○○ 파트에서 다룹니다)*` 로 표시합니다.

### 4.2 담당 범위

| 섹션 | 주 담당 |
| :--- | :--- |
| Ⅰ. 문제 정의 및 사용자 분석 | 공통 (서비스 기획) |
| Ⅱ. 기술 스택 선정 | 3팀 각각 자기 영역 |
| Ⅲ. 요구사항 분석 | 공통 |
| Ⅳ. 서비스 설계 | 서비스 서버 주도 · AI/클라이언트 보완 |
| Ⅴ. 화면 설계 | 클라이언트 |
| Ⅵ. 데이터 및 API 설계 | 서비스 서버 (AI 서버는 내부 API 계약만) |
| Ⅶ. AI 기능 설계 | AI 서버 |
| Ⅷ. 개발 환경 및 협업 방식 | 3팀 각각 |
| Ⅸ. 보안 및 배포 계획 | 3팀 각각 |

한 섹션을 여러 팀이 쓰는 경우 **한쪽을 지우지 말고 하위 항목으로 분리**합니다.

### 4.3 용어

| 대상 | 정본 표기 | 쓰지 않을 표현 |
| :--- | :--- | :--- |
| 캐릭터 | 타미(Tammy) | Tammy만 단독, TAMMY(전부 대문자) |
| Node.js 서버 | 서비스 서버 | 백엔드, 메인 서버, API 서버 |
| Go 서버 | AI 서버 | 모델 서버, 추론 서버 |
| React 앱 | 클라이언트 | 프론트, 앱 |

- 감정 상태 enum은 서비스 서버 Prisma `EmotionState`를 정본으로 하고, 다른 섹션은 그 값을 그대로 씁니다.
- 모듈 코드(`AUTH` / `CHT` / `FOD` / `TRV`)와 행성 코드(`MEAL` / `WATER` / `EMOTION` / `LIFESTYLE` / `RETROSPECT`)는 대문자 그대로 씁니다.

**미합의 — 팀 확인 필요**: 타미의 한 줄 정의가 세 레포에서 다릅니다.
"AI 가상 펫"(서비스 서버) / "공감형 픽셀 요정"(클라이언트) / "웰니스 펫 에이전트"(AI 서버).
Ⅰ장에서 하나로 확정한 뒤 이 표에 옮겨 적습니다.

### 4.4 사실 정합성

팀 경계에서 어긋나기 쉬운 항목은 **문서끼리 비교하지 말고 소스에서 확인**합니다.

- API 경로·메서드·헤더 → 호출하는 쪽과 받는 쪽 서술이 일치해야 합니다
- 데이터 모델 필드명 → 서비스 서버 Prisma 스키마가 정본입니다
- enum·상태값 목록 → 서비스 서버 정의가 정본이고 AI/클라이언트가 맞춥니다
- 모델명·성능 수치 → 실측값을 쓰고, 추정이면 추정임을 밝힙니다

같은 사실이 두 섹션에서 다르게 적혀 있으면 **그 자체를 정렬 실패로 봅니다.** 자동 병합 대상이 아닙니다.

### 4.5 서술 방식

- 경어체(`~합니다`)로 통일합니다.
- 근거 없는 수식어를 쓰지 않습니다. "빠릅니다"가 아니라 "약 2초입니다".
- 코드 블록은 명령어·설정 예시 수준까지만 넣습니다. 구현 코드는 넣지 않고 레포 경로로 참조합니다.
- 표는 `| :--- |` 정렬을 씁니다. 이모지는 제목에 쓰지 않습니다.
- 다이어그램은 `docs/images/`에 두고 상대 경로로 삽입합니다.

### 4.6 검토가 필요한 시점

- 팀원 PR을 main에 머지한 직후 (**필수**)
- 충돌을 손으로 해결한 직후
- 최종 제출 전 마지막 한 번

---

## 5. 작업 순서 요약

```bash
git switch -c docs/<이름>           # 담당 섹션 작성용 브랜치
# PLANNING_REPORT.md 의 담당 섹션 작성
git commit && git push -u origin HEAD
gh pr create                        # main 으로 PR

# 머지 후 (혹은 충돌 발생 시)
/report-align                       # 충돌 해결 + 전체 정렬 검토
```
