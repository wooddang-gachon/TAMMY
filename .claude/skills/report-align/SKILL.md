# 기획 보고서 정렬 검토

여러 팀원이 `PLANNING_REPORT.md`의 서로 다른 섹션을 각자 채워 PR을 올린다.
머지 시점마다 이 스킬로 **충돌을 해결하고 → 전체 문서가 한 방향을 보는지 검토한다.**

정렬의 정본은 **`README.md`의 "정렬 원칙" 절**이다. 판단이 갈릴 때는 README를 근거로 삼고,
README에도 답이 없으면 **추측하지 말고 사용자에게 묻는다.**

---

## 0. 시작 전 반드시 읽을 것

1. `README.md` — 특히 "정렬 원칙" 절 (정본)
2. `PLANNING_REPORT.md` — **전체를 읽는다.** 바뀐 부분만 보면 정렬 검토가 성립하지 않는다
3. `git log --oneline -5 -- PLANNING_REPORT.md` — 이번에 누가 무엇을 머지했는지

---

## 1단계 — 충돌 해결

`PLANNING_REPORT.md`에 `<<<<<<<` / `=======` / `>>>>>>>` 가 남아 있는지 먼저 확인한다.

```
grep -n '^\(<<<<<<<\|=======\|>>>>>>>\)' PLANNING_REPORT.md
```

없으면 2단계로 넘어간다. 있으면 **충돌 블록마다** 아래 순서로 판단한다.

### 판단 순서

| # | 상황 | 처리 |
| :-- | :--- | :--- |
| 1 | 서로 **다른 섹션**을 건드렸는데 충돌 (템플릿 공백 줄 때문) | 양쪽 다 살린다. 문서 목차 순서대로 배치 |
| 2 | **같은 섹션**을 각자 자기 도메인 관점에서 채움 | 양쪽 다 살리되 **하위 항목으로 분리**한다 (예: `### 2. 핵심 API 명세` 아래 서비스 서버 / AI 서버 표를 나란히). 한쪽을 지우지 않는다 |
| 3 | **같은 사실**을 다르게 서술 (모델명, 수치, enum, 엔드포인트 등) | **자동 해결 금지.** 어느 쪽이 실제 코드와 맞는지 해당 레포에서 확인한 뒤, 근거와 함께 사용자에게 확인받는다 |
| 4 | 한쪽이 템플릿 공백(`- **항목**: ` 빈 값), 다른 쪽이 실제 내용 | 실제 내용을 택한다 |
| 5 | 문체·표기만 다르고 내용은 같음 | README 정렬 원칙의 표기 규칙을 따르는 쪽으로 통일 |

3번은 이 레포에서 가장 중요한 충돌 유형이다. **서둘러 봉합하지 말고 반드시 물어본다.**

해결한 뒤 conflict marker가 전부 사라졌는지 위 grep으로 다시 확인한다.

## 2단계 — 전체 정렬 검토

문서 전체를 읽고 아래 5개 축을 각각 점검한다. 축마다 발견한 것을 **파일 내 위치(섹션 번호)와 함께** 기록한다.

### 축 1. 목차 구조

- 템플릿의 고정 목차(`Ⅰ ~ Ⅸ`)와 `##` / `###` 제목이 **글자 그대로** 일치하는가
- 팀원이 임의로 추가한 섹션이 있는가 → 있으면 기존 목차 안으로 흡수 가능한지 판단
- 자기 담당이 아닌 섹션을 삭제해버렸는가 → 삭제 금지. 비워두거나 `*(○○ 파트에서 다룹니다)*` 로 표시
- **아무도 채우지 않은 섹션**이 있는가 → 공백 목록으로 보고 (누락은 충돌보다 발견이 늦다)

### 축 2. 서비스 정의와 용어

- 서비스를 한 줄로 정의한 문장이 섹션마다 다르게 서술되지 않는가
- 고유명사 표기가 흔들리지 않는가 (예: 타미/Tammy, 별여행, 행성명, 모듈 코드)
- 같은 대상을 팀마다 다른 이름으로 부르지 않는가 (예: "서비스 서버" vs "백엔드" vs "메인 서버")

### 축 3. 사실 정합성 ← 가장 중요

팀 간 경계에서 어긋나기 쉬운 것들을 **교차 확인**한다.

- API 경로·메서드·헤더가 호출하는 쪽과 받는 쪽 서술에서 일치하는가
- enum / 상태값 목록이 서로 같은가 (예: 감정 상태 `HAPPY`/`SAD`/`ANGRY`/`STRESSED`/`CALM`)
- 데이터 모델 필드명이 프론트·백엔드·AI 서술에서 같은가
- 모델명·버전·성능 수치가 섹션마다 다르지 않은가
- 한쪽만 존재한다고 서술하는 기능이 있는가 (예: 프론트에는 있는데 API 명세에 없는 화면)

의심되면 **해당 레포 소스에서 실제 값을 확인한다.** `NASA_backEnd-main/`, `NASA_frontEnd-master/`, `tammy-ai-server-main/`.
문서끼리 비교만 해서 판정하지 않는다.

### 축 4. 서술 수준과 톤

- 경어체(`~합니다`)로 통일되어 있는가
- 어떤 섹션은 구현 디테일까지, 어떤 섹션은 한 줄 요약만 — 이런 **깊이 편차**가 심한가
- 표/불릿/이모지 사용 방식이 섹션마다 따로 노는가
- 코드·설정 파일을 그대로 붙여넣은 곳이 있는가 (기획 보고서에는 부적합)

### 축 5. 중복과 모순

- 같은 내용이 두 섹션에 중복 서술되어 있는가 → 어느 섹션이 정본인지 정하고 나머지는 참조로
- 서로 모순되는 주장이 있는가 (예: 한쪽은 "캐싱한다", 다른 쪽은 "매번 조회한다")
- 특정 팀 레포에서만 말이 되는 서술이 전체 서비스 설명처럼 쓰여 있는가

## 3단계 — 반영

발견한 항목을 두 부류로 나눈다.

### 직접 고친다 (판단 여지 없는 것만)

- 목차 제목 오탈자·번호 어긋남·순서 뒤바뀜
- 고유명사 표기 통일 (정본 표기가 README에 있을 때만)
- 문체 통일 (`~한다` → `~합니다`)
- 마크다운 문법 깨짐, 표 정렬, 중복된 구분선
- 명백한 잔재 (템플릿 안내 문구, conflict marker 찌꺼기)

고친 것은 전부 결과 보고에 **무엇을 어떻게 바꿨는지** 남긴다. 조용히 고치지 않는다.

### 물어본다 (내용 판단이 필요한 것)

- 사실이 서로 다를 때 → 어느 쪽이 맞는지
- 서술 범위가 겹칠 때 → 어느 섹션을 정본으로 할지
- 방향 자체가 갈릴 때 → 어느 방향으로 맞출지
- README 정렬 원칙에 없는 새 규칙이 필요할 때 → 원칙에 추가할지

물을 때는 **선택지와 각각의 근거를 함께** 제시한다. "정렬이 안 맞습니다"만 말하지 않는다.

## 4단계 — 결과 보고

아래 형식으로 출력한다. 항목이 없는 구획은 "없음"으로 남긴다(생략하지 않는다).

```markdown
## 정렬 검토 결과

**검토 대상**: PLANNING_REPORT.md (<총 줄 수>줄) · 직전 머지: <커밋/브랜치>

### 충돌 해결
- <해결한 충돌과 택한 근거> / 없으면 "충돌 없음"

### 직접 수정함
| 위치 | 내용 | 근거 |
| :--- | :--- | :--- |

### 확인 필요 — 사실 불일치
| 위치 | A 서술 | B 서술 | 소스 확인 결과 |
| :--- | :--- | :--- | :--- |

### 확인 필요 — 방향 판단
- <선택지와 근거>

### 미작성 섹션
- <아무도 채우지 않은 섹션 목록>

### 정렬 상태
<한 줄 판정: 정렬됨 / 부분 정렬 / 정렬 필요> + 근거 한 줄
```

## 하지 말 것

- 팀원이 쓴 내용을 **요약하거나 압축하지 않는다.** 정렬은 문장을 줄이는 작업이 아니다
- 사실 불일치를 임의로 한쪽으로 정리하고 넘어가지 않는다
- 자기 담당이 아닌 섹션이 비어 있다고 대신 채워 넣지 않는다 (누락으로 보고만 한다)
- 문서만 보고 코드가 그렇다고 단정하지 않는다. 확인 가능하면 소스를 연다
